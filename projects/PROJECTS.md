# Проекты
Этот файл — инструкции. Данные о проектах — в [[projects/index.json]]. Связи между файлами проектов — в [[projects/index.md]]. Шаблон нового проекта — в [[projects/_template.json]].
## Что такое проект
Проект — изолированный рабочий контекст. У него есть:
- запись в манифесте ([[projects/index.json]])
- папка в MemFS (`projects/<name>/`) с описанием
- физическая папка на диске (`physical_path`) с рабочими файлами
MemFS хранит **описание** проекта, не его файлы.
## Что в MemFS не хранится
**Структура физических папок.** Она живёт на диске и меняется по ходу работы. Описывать её в MemFS бессмысленно — описание устареет, синхронизировать невозможно. Агент может посмотреть содержимое папки через `ls`/`Glob` за секунду.
Описание структуры появляется в `notes.md` только когда оно **неочевидно** (например, «данные лежат не в `input/`, а в корпоративной шаре»). Текущее состояние папок не описывается.
## Файлы проекта в MemFS
Фиксированные имена. Внутри проекта — только файлы, за исключением
служебной подпапки `project-rules/` (см. «Регламенты» ниже).
| Файл | Обязательность | Назначение |
|---|---|---|
| `config.md` | обязательный | Пути, инструменты, git |
| `notes.md` | обязательный | Смысл проекта, специфика, контекст |
| `tasks.md` | обязательный | Что делается, что в планах. Статус — только в JSON |
| `skills.md` | опциональный | Две части: какие общие скиллы грузить в проекте; какие скиллы project-scoped |
| `glossary.md` | опциональный | Термины, специфичные для проекта |
| `project-rules.md` | опциональный | Оглавление регламентов и справочников проекта (если заполнена папка `project-rules/`) |
Файлы `skills.md`, `glossary.md`, `project-rules.md` создаются только когда есть контент. Не создавать «на всякий случай».
## Работа с файлами проекта
### Когда читать файлы проекта
При переключении на проект (после `config.md` и `notes.md`):
- Если в проекте есть `glossary.md` — прочитать перед работой с терминами, специфичными для проекта
- Если в проекте есть `project-rules.md` — открыть оглавление и прочитать нужное из `project-rules/` перед работой с формами документов, регламентами или спецификой проекта
- Если в проекте есть `skills.md` — загружать перечисленные там общие скиллы. Project-scoped скиллы подхватываются сами, когда CWD диалога = папка проекта
### Глоссарий (`glossary.md`)
Назначение: хранить термины, которые **в контексте этого проекта** означают не то же, что в общем языке или в других проектах.
Когда читать: перед любой работой с терминологией проекта (документы, отчёты, обсуждения с пользователем).
Когда писать: когда пользователь уточнил, что в контексте проекта термин означает именно X, а не Y. Когда обнаружилось, что термин понимается неоднозначно. Когда термин пришёл из внешней системы (1С, корпоративный стандарт) и означает там конкретное.
Формат: таблица «Термин | Варианты написания | Определение в контексте проекта».
### Регламенты (`project-rules/`)
Регламенты — все проектно-зависимые правила, справочники, шаблоны,
заметки из опыта. Хранятся в подпапке `project-rules/`.
Оглавление — `project-rules.md` в корне проекта, по образу
`lessons.md` → `lessons/`.

В `project-rules/` кладётся всё дополнительное знание проекта,
не вошедшее в config.md, notes.md, tasks.md, glossary.md, skills.md.
Никакого внутреннего разделения на «уроки» и «правила» — одна папка
для всей специфики проекта: проектный урок и проектное правило неотличимы
друг от друга.
Разграничение с общим слоем: если знание повторится в другом проекте —
оно общее, идёт в `reference/lessons/`. Если это нюансы только этого
проекта — в `project-rules/`.

Когда читать: после config.md и notes.md, если предстоит работа
с формами документов, регламентами или спецификой проекта.
## Добавление нового проекта
1. Прочитать шаблон [[projects/_template.json]] — какие поля заполнять, какие файлы создавать
2. Создать папку `projects/<name_en>/`
3. Создать обязательные файлы: `config.md`, `notes.md`, `tasks.md`
4. Если есть скиллы, термины, регламенты — создать соответствующие файлы и папку `project-rules/`
5. Создать физическую папку на диске по `physical_path` (пользователь указывает путь) со стандартными подпапками из шаблона
6. Добавить запись в `projects` в [[projects/index.json]]
7. **Добавить `[[path]]`-ссылки в [[projects/index.md]]** — иначе граф памяти не увидит файлы
8. Обновить `statistics` в [[projects/index.json]]
## Переключение проекта
1. Прочитать [[projects/index.json]] — есть ли проект в `projects`
2. Если нет — проверить `archived`
3. Если найден — прочитать `projects/<name>/config.md` и `notes.md`
4. Если не найден — сообщить пользователю и предложить список
## Текущий проект и изоляция контекстов
Текущий проект хранится в блоке памяти `current_project`. Перед любым действием, связанным с проектом, проверь это значение. Если блок пуст — спроси пользователя.
Каждый диалог может быть посвящён одному проекту. В начале нового диалога пользователь говорит, над каким проектом работаем — устанавливаешь контекст и читаешь `config.md`, `notes.md`, `tasks.md`. Если пользователь создаёт второй диалог по тому же проекту — снова прочитать `config.md` (освежить память) и работать с теми же правилами.
Важно: не смешивай данные разных проектов. Используй только файлы текущего проекта.

## Пути проектов и CWD

У каждого проекта есть physical_path — корневая папка на диске.
Хранится в index.json. Сводка — в таблице ниже.

При переключении на проект — установить CWD диалога = physical_path
через SetWorkingDirectory.

При ручной смене CWD через иконку папки:
- если новый CWD — подпапка physical_path активного проекта — ничего не менять
- если новый CWD = physical_path другого проекта — считать это переключением
- если новый CWD не соответствует ни одному проекту — сообщить пользователю,
  спросить, что делать

| environment-compass | <диск пользователя>\Git-projects\environment-compass |
| <проект 2> | <CWD агента>\<проект 2> |

## Скиллы и проект

### Что пишется в `projects/<name>/skills.md`
Файл содержит две независимые части:
- **Какие общие скиллы грузить в проекте.** Список имён; при желании — что не грузить. Это рекомендации, сами скиллы лежат в общих областях (`$MEMORY_DIR/skills/`, `~/.letta/skills/`, встроенные) и в MemFS не дублируются.
- **Какие скиллы здесь project-scoped.** Имя и пометка «project-scoped». Сам скилл лежит на диске проекта (см. ниже), в MemFS не кладётся.

Строка «project-scoped» всегда означает файл на диске проекта, а не копию в MemFS.

### Project-scoped скилл
Скилл, специфичный для одного проекта, лежит на диске по пути:
    <physical_path>\.agents\skills\<имя_скилла>\SKILL.md
Это файловая система проекта, не MemFS. В MemFS скилл не кладётся.

Когда поступает запрос «сделай скилл только для проекта»:
1. Создать папку `<physical_path>\.agents\skills\<имя_скилла>\`
2. Создать SKILL.md с frontmatter (name, description)
3. Убедиться, что CWD диалога = physical_path проекта
   (скилл подхватится при следующем ходу, придёт system-reminder)
4. В projects/<name>/skills.md добавить строку с именем скилла
   и пометкой, что он project-scoped

Штатной команды для установки в .agents/skills/ у Letta нет.
Только ручное создание файла.

Ограничения:
- не версионируется в MemFS — только в git проекта, если он есть
- не переносится между машинами автоматически
- не виден другим агентам
- работает, только когда CWD диалога = папка проекта

### Области видимости скиллов и приоритет

| Приоритет | Область | Путь | Доступен |
|---|---|---|---|
| 1 | Project | `<physical_path>\.agents\skills\` | только когда CWD диалога = папка проекта |
| 2 | Agent | `$MEMORY_DIR/skills/` | всегда, в любом проекте |
| 3 | Computer | `~/.letta/skills/` | всегда, на этой машине |
| 4 | Bundled | внутри Letta Code | всегда |

При совпадении имён выигрывает высший приоритет: project перекрывает agent, agent — computer, computer — bundled.
Список доступных скиллов — команда `/skills`.
Скилл из памяти агента (`$MEMORY_DIR/skills/`) или из `~/.letta/skills/` доступен всегда — дублировать его в проект бессмысленно: придётся поддерживать две версии.
