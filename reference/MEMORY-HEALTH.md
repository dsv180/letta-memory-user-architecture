# Здоровье памяти
Метрики и процедуры проверки. Периодичность и механизмы обслуживания — [[memory-design/lifecycle.md]] («Проактивное обслуживание памяти»).

## Что проверять
- **Бюджет ядра.** Файлы `system/` лежат в промпте каждый ход — следить за их размером в токенах; раздувание ядра удорожает каждый ход ([[memory-design/architecture.md]]).
- **Устаревшие и нечитаемые уроки.** Уроки, которые перестали применяться, противоречат другим или ссылаются на удалённое.
- **Дубли.** Одно знание в нескольких местах ([[reference/lessons.md]], «Уроки — живой слой» — дополнять, а не дублировать).
- **Устаревшие правила `reference/`.** Битые и короткие `[[path]]`-ссылки, устаревшие пути, ссылки на исчезнувшие файлы.
- **Структура.** Файлы на своих слоях; индексы (`lessons.md`, `index.json`, `index.md`) согласованы с содержимым.
- **Frontmatter.** У каждого `.md` он цел и валиден: первая строка `---`, есть `description:` (версия — внутри). Теряется при правках вне `memory()` (Write/скрипт/мод) — проверять после них и массово скриптом.

## Требования (вход валидатора)
Точные, машинно-проверяемые условия скрипта-валидатора (#7); «Что проверять» выше — области ручного аудита. Источник каждого требования — канон.
- **Frontmatter.** Каждый `.md` начинается с `---`; есть `description` (версия — внутри него); других ключей, кроме `description`, `read_only`, `limit`, нет ([[lessons/yaml.md]]). Исключение — `skills/<name>/SKILL.md`: у скиллов свой frontmatter (`name`, `description`, `version`).
- **Версии.** `version` в описаниях и `memory_version` в `memory-design/manifest.json` совпадают ([[memory-design/architecture.md]]). Скиллы и файлы-хроники (`*/journal.md`, `memory-design/deltas/*`) вне проверки: у скиллов своя версия, хроникам `version` не нужен.
- **Ссылки.** Все `[[...]]` — полный путь от корня памяти и ведут в существующий файл; коротких и битых нет. Примеры вида `[[path]]` или `[[...]]` в обратных кавычках — иллюстрация, не ссылка, валидатор их пропускает.
- **Папки верхнего уровня.** Только `system/`, `reference/`, `lessons/`, `project/`, `memory-design/`, `skills/`; служебные `.git`, `state/`, `profile.png` — вне проверки.
- **Слои.** Файл лежит на своём слое; служебное слоя `project/` (инструкции, манифест, связи, шаблон) — в `reference/`; скиллы — в `skills/<name>/SKILL.md`.
- **Проект.** Каждая папка `project/<name>/` содержит обязательные `config.md`, `notes.md`, `tasks.md`.
- **Манифест.** `manifest.json` — валидный JSON; `canon`/`local` согласованы с фактическим размещением.
- **Индексы.** `lessons.md`, `index.json`, `index.md` согласованы с содержимым: `lessons.md` перечисляет все `lessons/*.md`, `index.md` — все файлы `project/**`, поля `latest_tag` и `statistics` в `index.json` отражают выпущенную версию.
- **Форма записи.** Заголовок-тема без дат, имён и скобок; нет дат вида `(дд.мм.гггг)` и атрибуций («по команде …», «по просьбе …») вне файлов-хроник (`*/journal.md`, `*/tasks.md`, `memory-design/deltas/*`); нет личных форм; один тип маркера списка на файл (нумерация — только шаги процедур; смешение машина помечает сигналом, вердикт даёт ревьюер); команды — в обратных кавычках ([[memory-design/architecture.md]], «Формат записи знания»).
- **Размер и порядок.** Файл — не больше ≈150 строк; в начале — сводка. Порядок разделов — по значимости и частоте применения, не по дате. Размер проверяет машина, порядок — ревьюер.
- **Оглавление.** У каждого пункта `lessons.md` есть строка «когда применять».

## Инструменты
| Инструмент | Что даёт |
|---|---|
| `/doctor` | аудит размещения памяти, дублей, размера промпта |
| `/init` | пересборка/освежение памяти по проекту |
| `/remember` | зафиксировать урок из текущего диалога |
| `letta messages search` | поиск по истории — не обсуждалось ли ранее |
| мод MemFS Search (`memfs_search`) или `Grep` | поиск по файлам памяти |

Автоматический валидатор структуры (битые/короткие ссылки, выход за слои, потеря/дублирование frontmatter) — задача #7: требования в канон, скрипт — отдельным заходом в клон.

## Регулярность
- Содержательная консолидация — dreaming (`/sleeptime`).
- Периодические проверки целостности — `letta cron` (на local-backend тикает при открытой сессии).
- Бэкап: local-only агенты отвечают за него сами; в облаке версионирование на стороне сервиса.
