# Жизненный цикл памяти
Процедуры: как менять структуру памяти и как выпускать её версии.
Устройство памяти — в [[memory-design/architecture.md]]. Применение архитектуры к своей памяти (внедрение) — в [[memory-design/migration.md]].
Здесь регламент, а не урок: уроки (знание из опыта) живут в `lessons/`, и процедуру выпуска версии туда не дублировать.
Конкретика рабочего репозитория версий (URL, клон, бэкап, скрипты `tools/`) — в локальных регламентах проекта архитектуры памяти (в публичный слепок не входят).

## Добавление файла
1. Определить слой: `system/`, `reference/`, `lessons/`, `project/`, `memory-design/`.
2. `reference/` — дописать ссылку в `lessons.md` (если это урок) или в раздел слоёв architecture.md.
3. `lessons/` — дописать ссылку в оглавлении `reference/lessons.md`.
4. `project/` — запись в `reference/index.json` и `[[path]]`-ссылка в `reference/index.md`.
5. Проставить `version: 1.Х` внутри `description`.

## Удаление файла
1. Убедиться, что информация не дублируется.
2. Убрать ссылку из индекса (`lessons.md` / `index.json` / `index.md`).
3. Удалить файл.

## Переезд и переименование файла
1. Переместить файл: `git mv <старый> <новый>` (не «удалить + создать» — иначе теряется история).
2. Найти все ссылки на старый путь по всей памяти (Grep) и заменить на новый полный путь.
3. Обновить индексы, где путь указан явно: `reference/lessons.md`, `reference/index.json`, `reference/index.md`.
4. Повторить поиск — старых ссылок быть не должно. Автоматический поиск коротких и битых ссылок — в валидаторе (#7).
5. Коммит.

## Выпуск новой версии (разработчик канона)
Слепок — снимок структуры памяти; живая память остаётся в `$MEMORY_DIR`.
Новая версия — когда меняется **структура или правила**, а не содержимое проектов.
Версия репозитория — это **тег и Release**, а не папка: файлы версии лежат в корне репозитория.

1. Бэкап всей папки `memory/`.
2. Проверить чистоту живой памяти: `git -C "$env:MEMORY_DIR" status --short` — пусто, иначе разобрать.
3. Привести слои к новой версии, сверить с целевой.
4. Финализировать дельту перехода `memory-design/deltas/<версия>.md` (что изменилось от предыдущей версии).
5. Поднять `version` в каждом `description` живой памяти: `tools/bump-version.py <старая> <новая> --root "$env:MEMORY_DIR"`.
6. Выставить `memory_version` в [[memory-design/manifest.json]] на новую версию.
7. Скопировать в корень репозитория пять папок — `system`, `reference`, `lessons`, `project`, `memory-design` — обязательно с `\*` у источника, иначе папка вложится подпапкой. `system-prompt/` в репозитории уже лежит.
8. Обезличить конвейером `tools/` ([[memory-design/publication.md]]): он заменит личное и уберёт из слепка локальные файлы (секция `local_files`) — вручную их удалять не нужно.
9. Гейт: `check-anonymized.py` → `exit 0`.
10. Дописать раздел в `CHANGELOG.md`.
11. Коммит и push в ветку репозитория версий.
12. Поставить на новый коммит **новый** тег (`v1.Х`) и опубликовать Release. Теги не переставлять: выпущенный тег неизменяем.

## Обновление своей живой памяти (по дельте)
Выпуск версии и переход своей памяти на неё — разные процедуры: выше — **выпуск** (разработчик канона), здесь — **переход** (потребитель, даже если это тот же агент).
1. Проверить `memory_version` в [[memory-design/manifest.json]] — это источник перехода.
2. Открыть дельту `memory-design/deltas/<целевая>.md` и применить её.
3. Пропуск версий: применять дельты **последовательно** (1.5 → 1.6 → 1.7). Нет дельты нужного шага (слишком старая версия) — fallback: сверка с каноном по содержимому ([[memory-design/migration.md]]).
4. Личное (`project/`, `system/persona.md`, `system/human.md`) не трогать.
5. Поднять `version` файлов (`tools/bump-version.py`) и `memory_version` в [[memory-design/manifest.json]].

## Откат версии
Вернуть канонный слой к более ранней версии, не трогая личное. Теги версий живут в репозитории версий (клон), не в живой памяти.
1. Бэкап `memory/`.
2. Взять слои канона из тега нужной версии (`git -C <клон> checkout v<версия>`) и применить к живой памяти по [[memory-design/migration.md]] — личное (`project/`, `system/persona.md`, `system/human.md`) не трогать.
3. Вернуть `memory_version` в [[memory-design/manifest.json]] на прежнюю.
Полный откат всей памяти — из бэкапа.

## Обезличивание (обязательный шаг выпуска)
Слепок публикуется в открытый репозиторий, поэтому коммит версии — только после обезличивания. Правила, конвейер `tools/` и типовые ошибки — в [[memory-design/publication.md]].

## Смена истории репозитория
`git filter-repo --replace-text` не годится, если в репозитории есть служебные файлы, где сами паттерны хранятся как данные (правила обезличивания): замены применяются ко всей истории и ломают такие файлы.
Способ — **сброс истории**: `git checkout --orphan` → один чистый коммит текущего дерева → force-push в основную ветку + переставить тег.
Обязателен бэкап клона (копия папки целиком) — старая история остаётся только там.
Специфика `filter-repo` на Windows — в [[lessons/git-local.md]].

## Рантайм мода в `state/`
Моды (например statusline) пишут состояние в `$MEMORY_DIR/state/` (например `emotions.json`). Это не память: `state/` не коммитится и в слепок не входит.
Если установлен мод, пишущий в `state/`, исключи папку из git — это личный ignore, он не коммитится:
    echo 'state/' >> "$env:MEMORY_DIR/.git/info/exclude"
После этого изменения в `state/` не мешают `memory()` (оно требует чистого дерева) и не попадают в память.

## Проактивное обслуживание памяти
Чтобы память не копила мусор, часть обслуживания выносится в фон.
**Dreaming** (`/sleeptime`) — основной механизм: фоновые субагенты памяти пересматривают недавние беседы, консолидируют уроки и правят память, не прерывая работу. Запуск — по числу завершённых шагов агента или при сжатии контекста; есть опция «агент проверяет перед применением» (изменения ждут подтверждения). Настраивается в CLI (`/sleeptime`) или в приложении (Dream settings).
**Планировщик `letta cron`** — общий: напоминания и периодические задачи (например ночная проверка целостности `reference/`, обновление `active-work.md`). На local-backend расписания тикают только при открытой сессии (`~/.letta/cron.json`); на Cloud планировщик серверный.
Разделение: содержательное обслуживание памяти — dreaming; регулярные проверки и напоминания — cron. Ручные аналоги — `/init` (пересборка по проекту), `/doctor` (аудит размещения, дублей, размера промпта), `/remember` (записать урок).

## Типовые ошибки
- Копирование без `\*` у источника вкладывает папку подпапкой — [[lessons/windows-guide.md]].
- `git add` с несуществующим путём не стейджит ничего — после коммита проверять `git status --short` и `git log --oneline -1` ([[lessons/git-local.md]]).
- Незакоммиченные изменения в `state/` — норма для модов, а не дефект памяти: `memory()` требует чистого дерева и падает. Лечится исключением `state/` через `.git/info/exclude`.
- Ошибки обезличивания (имена, идентификаторы машины, ссылки, `forbidden_patterns`) — в [[memory-design/publication.md]].
