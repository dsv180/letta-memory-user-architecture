# Letta Desktop — изнанка
Как LД на самом деле ведёт диалоги и строит карту памяти. Проверено по файлам и коду ЛД 0.32.19, а не по догадкам.

## Папка диалога и Desktop-«проекты»
- Папка каждого диалога — в `~/.letta/desktop-cwd-map.json` (карта «id диалога → путь»).
- «Проект» в интерфейсе ЛД — это и есть папка CWD диалога. Служебные файлы диалога лежат в `~/.letta/projects/<путь-в-кодировке>/`: двоеточие и обратный слэш заменяются подчёркиванием (домашняя папка на Windows → `C__Users_<имя>`), внутри — `agent-tools/` с выгрузками больших выводов инструментов. Больше «диалогового» там ничего нет.
- Папка старта новых диалогов — `defaultWorkingDirectory` в `~/.letta/desktop_preferences.json`.
- `SetWorkingDirectory` меняет CWD только в сессии и бэкенде. Карту `desktop-cwd-map.json` ведёт Desktop и обновляет её, когда папку выбирают в интерфейсе (иконка папки). Значит канонное «при переключении на проект установить CWD через `SetWorkingDirectory`» описывает половину механизма: привязка диалога в интерфейсе так не переезжает.
- Память и проекты привязаны к **агенту** (MemFS), а не к диалогу: новый диалог видит ту же память целиком, ничего не теряется. Обратная сторона — старый длинный диалог дорог (компакция уже срабатывала) и заметно сильнее срывается в цикл повторов; свежий диалог лечит симптом, но **до** его старта память надо закоммитить, иначе новый диалог свежих правок не увидит.

## Модель и провайдер
- Модель **диалога** лежит в `~/.letta/lc-local-backend/conversations/<id>/conversation.json`, поле `model`: у нас `openai-compatible/deepseek-v4.1-flash`. Провайдер, его `base_url` и где лежит ключ — [[lessons/aitunnel.md]].
- **Имя диалога** в списке ЛД — поле `summary` в том же `conversation.json` (папка диалога = base64 от `conversation:<id>`). Правится прямо на диске; backend правку сохраняет, в списке обновляется при перечитывании: `Ghbdtn` → `Выпуск 1.6 архитектуры памяти`).
- Поле `model` в файле агента (`agents/<id>.json`) — **остаток, не источник истины**: модель диалога его перекрывает. Смотреть модель надо из `conversation.json` (агент доложил `openai/gpt-5.5` из файла агента).
- `deepseek-v4.1-flash` на длинном рассуждении срывается в цикл повторов («Хм» — до тысяч токенов подряд; в thinking-блоках). Это деградация генерации, а не память: промптом не лечится, рычаг — параметр против повторов у провайдера либо смена модели.
- Рассуждения (`thinking`) пользователь читает в интерфейсе, поэтому предлагать отключить или урезать их нельзя. Снижение `max_output_tokens` цикл не лечит (обрезает только полезную длину) — обе эти рекомендации агент выдал и снял. В настройках диалога сейчас только `provider_type`, `context_window_limit`, `max_tokens`, `parallel_tool_calls`, `max_output_tokens`; параметра против повторов нет.
- **Сбой чтения инструментов:** в длинном диалоге все вызовы (и `Read`, и Bash) могут начать возвращать пустой результат, хотя команды выполняются. Это сбой среды/сессии, не памяти. Лечение — перезапуск ЛД или новый диалог; **до** перезапуска закоммитить память, иначе правки пропадут для нового диалога.

## Компакция контекста
- `/compact` — встроенная команда харнеса/Desktop, а не инструмент агента: я её не запускаю и «повторить» не могу.
- Компакция может пройти **молча**: при `"showCompactions": false` в `~/.letta/settings.json` интерфейс не показывает ни активность, ни отчёт — отсюда жалоба «дал команду, не вижу исполнения».
- Надёжный признак, что сжатие реально прошло, — системный маркер `Conversation history was compacted` сразу после команды, а не отчёт в UI. Состояние настройки смотреть конфигурацией (встроенный скилл `self-configuration`), а не догадками.
- При CWD = домашней папке файл `~/.letta/settings.json` читается и как user, и как project scope — это один и тот же ключ.

## Граф памяти
- Узлы — файлы памяти, рёбра — ссылки `[[...]]`, рамки — группы. Рёбра строятся по ссылкам, поэтому `index.md` выглядит центральным хабом.
- Группа считается по **пути файла**, а не по плотности связей: функция `getGroupKey` в коде ЛД берёт первый сегмент пути, для скиллов ключ — `skills`.
- Спец-правило для проектов зашито на корневую папку **`project` (единственное число)**: `project/<имя>/...` даёт отдельную рамку на проект, подпись — последний сегмент капсом, дефисы и подчёркивания → пробелы (`_probe` → `PROBE`).
- Одноимённые файлы разных проектов не сливаются: узел = файл с полным относительным путём, совпадают только подписи (basename). Именно это и создаёт «кашу» внутри общей рамки.
- Проверка гипотезы без правок: завести в памяти `project/_probe/notes.md`, **закоммитить** и обновить граф (Refresh на вкладке Memory) — появляется отдельная рамка `PROBE` с одним узлом.
- Было при корне `projects/` (мн. ч.): срабатывало общее правило «группа = первый сегмент» → все проекты в одной рамке `PROJECTS`. Это расхождение в самой Letta: встроенный скилл `initializing-memory` учит канону `projects/<имя>/...` и запрещает generic `project/`, а код графа ждёт `project/`.
- Лечится переименованием корневой папки `projects/` → `project/`; правок в ЛД не нужно. Плюс к тому — баг-репорт в ЛД. Сделано: память переименована, граф разделил проекты по рамкам.
- **Группа = папка верхнего уровня** (подтверждено экспериментом): `reference/lessons/` (17 файлов) отдельной рамки не давала, а после переноса на верхний уровень (`lessons/`) появилась рамка `LESSONS` (18 узлов). Файл-индекс `reference/lessons.md` при этом остался в рамке `REFERENCE` — рамку задаёт папка, а не файл.
- **Исключение из правила:** подпапка даёт свою рамку только внутри `project/` — спец-ветка захардкожена на строку `project`. Поэтому у проектов разделение работает, а вложенные подпапки других слоёв отдельной рамки не получают.
- Текущий корень памяти: `lessons/`, `memory-design/`, `project/`, `reference/`, `skills/`, `system/` (+ `profile.png`).
- **Файлы уровня корня `project/` дают фантомную рамку `PROJECT`** — ключ группы для них становится вторым сегментом пути, то есть именем самого файла. Рамку задают файлы уровня папки, а не папки проектов; проекты при этом остаются раздельными. Лечится переносом служебных файлов слоя (`PROJECTS.md`, `index.md`, `index.json`, `_template.json`) в `reference/` — сделано, рамки `PROJECT` больше нет, в слое `project/` остались только папки проектов.
- **Граф и дерево строятся из закоммиченного состояния (`HEAD`), а не из рабочего дерева** (ранее было открытым вопросом): незакоммиченный перенос в графе не отражался, после коммита рамка появилась сразу при переключении вкладки, без перезапуска. Правило: сначала коммит, потом смотрим граф.
- Описания графа «от другой модели» (группировка по плотности связей, схлопывание одноимённых узлов, вина коротких ссылок) — гипотезы: визуальная часть может быть верной, объяснение — нет. Проверять по коду и файлам.

## Где смотреть код и настройки ЛД
- Установка: `%LOCALAPPDATA%\Programs\letta-code\resources\app.asar` (рядом `app.asar.unpacked`).
- Текстовый поиск прямо по `app.asar` находит исходники компонентов: `getGroupKey`, `buildLayout`, `buildGroups`, `MemoryGraph`, `toDisplayLabel`.
- Встроенные скиллы Letta (например `initializing-memory`) лежат внутри того же архива.
- Настройки Desktop: `~/.letta/desktop_preferences.json`; папки Desktop-проектов: `~/.letta/projects/`.
- **Я — Letta Desktop, репозиторий `letta-ai/letta-code` — харнес (CLI/App Server/runtime), который Desktop встраивает** (`app.asar` из того же пакета). Версия Desktop = ProductVersion `Letta.exe` (у нас 0.32.19), совпадает с версией встроенного харнеса. Обновление Desktop — его апдейтером/новым установщиком, не через npm; Desktop-сборка отстаёт от GitHub-релиза `letta-code` на 1–2 дня.
- **Куда сообщать о багах Letta Code:** в `letta-ai/letta-code` (не в `letta-ai/letta`, где issues не ведутся). Правила и форма issue — [[lessons/letta-code-issues.md]].
