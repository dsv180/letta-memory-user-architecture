# GitHub-гайд

Справочный файл. Читай, когда нужно работать с GitHub: клонировать, пушить, создавать релизы, публиковать проекты.

## Установка gh CLI

Установлен в `C:\Program Files\GitHub CLI\gh.exe`

Установка через winget (требует права администратора, UAC-запрос):
```powershell
winget install --id GitHub.cli --silent --accept-package-agreements --accept-source-agreements
```

## Авторизация

Авторизация через браузер (вход через Google SSO — аккаунт <логин>):
```powershell
gh auth login --web
```
После ввода одноразового кода — браузер откроет страницу входа через Google.

## git config

Локальный git настроен через `gh auth setup-git`:
- user.name: `<логин>`
- user.email: `<email>`
- Ветка по умолчанию: `main`

Проверить локальные настройки: `git config --local --get user.name`, `git config --local --get user.email`.

## Ограничения

**Trade controls restriction** — аккаунт <логин> не может создавать репозитории через API или `gh repo create`. Только через веб-интерфейс: `github.com/new`.

Публиковать можно только публичные репозитории (приватные заблокированы региональной политикой — аккаунт привязан к домашнему региону).

Смена видимости (public → private) и переименование — под тем же региональным риском; отдельно не проверялись. Поэтому «убрать персональное из публичного репо» решается **переписыванием существующего** репо, а не созданием или переименованием нового — детали в локальных регламентах проекта архитектуры памяти (в публичный слепок не входят).

Ограничение на уровне аккаунта/региона, а не сети: повторный тест в другом сетевом окружении дал ту же ошибку `GraphQL: Trade controls restricted owner can't create repositories.` Смена окружения его не снимает — не предлагать повторять этот тест «на другой сети».

## Клонирование репозитория

При запросе «склонируй репозиторий с GitHub» — сначала попробуй `git clone <url>` с таймаутом 120с+. Не предлагай SSH-ключи, токены, IP-адреса или другие обходные пути, пока простая команда не упала с конкретной ошибкой.
Если `git clone` не работает из-за прокси — попробуй `gh repo clone <owner>/<repo>` (GitHub CLI часто залогинен отдельно).
Не создавай репозиторий локально без явного разрешения — пользователь просит клонировать, а не создавать с нуля.

## Работа с существующими репозиториями

- `fetch`, `push`, `gh api`, `gh repo view` по уже существующим репозиториям **работают** (push в `letta-memory-user-architecture` прошёл). Блокирует только создание новых.
- Если в origin сделан force-push, локальный клон расходится (`ahead N, behind M`). Локальные коммиты не терять: сначала сохранить старую линию веткой (`git branch legacy-<ver> <sha>`), и только с разрешения пользователя делать `git reset --hard origin/master`. Детали — в локальных регламентах проекта архитектуры памяти (в публичный слепок не входят).
- При проверке облака после force-push: `git fetch origin --prune` и смотреть `refs/heads` в origin, а не доверять локальному кэшу.

## Чтение файла из репозитория без клона

Содержимое файла в конкретном теге или ветке читается через API, без захода в локальный клон (полезно, когда клона нет под рукой или нужен файл из конкретного тега):
```powershell
gh api repos/<owner>/<repo>/contents/<path>?ref=<tag-or-branch>
```
Содержимое приходит base64 в поле `.content`. В консоли Windows кириллица может отобразиться «кракозябрами» — это артефакт вывода, а не порча файла в репозитории.

## Issues, метки и milestones

- **Версия проекта в трекинге — это milestone**, а не метка: `gh api repos/<owner>/<repo>/milestones -f title=1.7 -f description="..."`. Метки оставляем для типа (`gap`, `enhancement`, `rejected`, `proposal`); одну версию в двух местах не держим.
- **Отклонение issue** — закрыть как непланируемое с причиной, а не как выполненное: `gh issue close <N> --reason "not planned"`, причина — комментарием (`gh issue comment <N> --body "..."`).
- **Milestone на issue:** `gh issue edit <N> --milestone "1.7"`.
- **Не сцеплять вызовы `gh api` конвейером** (`gh api ... | gh api ...`): вывод первой команды уходит во вторую в stdin, и результат теряется — из трёх milestones так создался только один. Каждую команду — отдельным вызовом; пакетные правки — циклом PowerShell, но с отдельными вызовами `gh` внутри.

## Работа с прокси

`gh` написан на Go и использует `ALL_PROXY`, а не `http_proxy`/`https_proxy`. При проблемах с подключением:
```powershell
$env:ALL_PROXY="http://proxy:port"
```

## Релизы

Для публикации новой версии:
```powershell
git tag v<version>
git push origin v<version>
gh release create v<version> --title "v<version>" --notes "..."
```

## Атрибуция публичных проектов

При публикации на GitHub обязательно указывать происхождение кода (ссылку на оригинал, автора, лицензию). Без атрибуции — серьёзный зашквар.

Весь публичный контент (README, описания) — только на русском, если пользователь не сказал иначе.
