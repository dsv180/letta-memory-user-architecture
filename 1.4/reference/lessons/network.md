# Сеть и DNS

Справочный файл. Читай, когда «нет интернета», не резолвятся домены, падает `git fetch`/`gh`.

## Диагностика (порядок)

1. Резолв: `Resolve-DnsName github.com`
2. Связность наружу: `Test-Connection 8.8.8.8` (ICMP) и `Test-NetConnection github.com -Port 443`
3. Какие резолверы прописаны: `Get-DnsClientServerAddress`
4. Альтернативный резолвер: `Resolve-DnsName github.com -Server 8.8.8.8`
5. Прокси-переменные окружения: `Get-ChildItem Env: | Where-Object { $_.Name -like "*PROXY*" }`

Ключевое различение: **ICMP проходит, а имена не резолвятся** → виноват резолвер, а не «GitHub заблокирован» и не блокировка сети. Вывод «недоступно» нельзя делать, проверив только один способ (см. [[reference/lessons.md]]).

## Известный случай: AdGuard VPN (23.09.2026)

На домашнем ПК стоит AdGuard VPN. Он прописывает свои DNS-серверы в системные настройки, а они отвечают только внутри туннеля. Если исключить приложение (ЛД, `git.exe`, PowerShell) из VPN — его запросы идут мимо туннеля, а системные DNS остаются «впн-овскими» → имена не резолвятся вообще.

Симптомы: `Resolve-DnsName` пусто для всех доменов, `Test-Connection 8.8.8.8` — True, прямой `-Server 8.8.8.8` тоже пусто (UDP/53 наружу блокируется).

Лечение: вернуть приложение в VPN либо отключить в AdGuard VPN перехват DNS (тогда система получит обычный DNS-сервер). Итог в тот раз: пользователь отключил AdGuard VPN — сеть заработала.

## Правило

Не предлагать костыли (обращение по IP, `--resolve`, правка hosts), пока не проверен и не объяснён резолвер. Сначала причина, потом обход.

## Урок: сетевая безопасность

- Сканировать порты и любую сетевую активность можно ТОЛЬКО на одном хосте, который явно указан в задаче. Полный запрет сканирования подсетей, диапазонов и нескольких хостов за один вызов. Нарушение — серьёзные последствия.
- Разрешённый адрес из практики: `<внутренний хост>`. Всё остальное — только по явному указанию в задаче.
